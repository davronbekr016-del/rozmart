# ROZMART Mini App

Telegram Mini App для сети магазинов ROZMART: каталог продукции ROZMETOV, заказ, доставка.

Требования и процесс описаны в папке `Загрузки\Проект ROZMART` — SRS, Регламент, BPMN-схема, прототипы.

## Карта функционала

Что уже готово — смотреть сюда до написания нового кода.

| Модуль | Что умеет | Неочевидное |
|---|---|---|
| `app/db.py` | Подключение к базе, `get_db`, `init_db` | Для SQLite включает `foreign_keys`, `WAL` и `busy_timeout` — без них запись заказа блокирует чтение каталога |
| `app/models.py` | `Category` → `Product` → `Variant`, `Order` → `OrderItem`, `Customer` | `Variant.price` может быть `NULL` (прайса ещё нет), но не `0`. `Product.is_active` по умолчанию `false` (BR-34). `Order.client_key` — ключ попытки оформления, `Order.telegram_id` — чей заказ |
| `app/profile.py` | `GET/PUT/DELETE /api/profile`, `save_customer` | Записи о покупателе без согласия не бывает: `consent_at` обязателен. Заказ профиль не переписывает (`update_existing=False`) — разовая доставка на чужой адрес не должна менять сохранённое. Удаление профиля не трогает оформленные заказы |
| `app/seed.py` | Наливает каталог из `data/catalog.json`, если товаров нет | На сервере база создаётся пустой: сам файл базы в репозиторий не едет |
| `app/telegram.py` | Проверка подписи Telegram, зависимости `current_user` / `require_user` / `buyer` | Без `BOT_TOKEN` приложение не стартует — тихая работа без проверки входа опаснее падения. Для разработки без Telegram: `TELEGRAM_AUTH_DISABLED=1`. Подпись живёт сутки |
| `app/schemas.py` | Что API отдаёт клиенту и что принимает | Служебных полей REGOS здесь нет намеренно (BR-36). Телефон нормализуется к `+998…` |
| `app/catalog.py` | `GET /api/categories`, `/api/products`, `/api/products/{id}` | Товар виден, только если активны и он, и хотя бы одна фасовка с ценой. Цена «от» — по видимым фасовкам (BR-37) |
| `app/orders.py` | `POST /api/orders`, `GET /api/my-orders`, `GET /api/delivery-price` | Суммы считает сервер по базе, тело запроса на цену не влияет. Повтор с тем же `client_key` возвращает прежний заказ, чужой ключ просто игнорируется. `expected_total` не сошёлся → 409. Наличные → `CONFIRMED`, онлайн → `NEW` (BR-13). Чтения заказа по номеру нет намеренно: номера идут подряд и перебирались бы |
| `scripts/import_catalog.py` | **Устарел.** Заливал 55 позиций и фото из Excel с диска разработчика | Оставлен для разовой заливки фотографий. Каталог теперь приезжает из REGOS |
| `app/regos/client.py` | Клиент REGOS API | API всегда отвечает HTTP 200, успех — по полю `ok`. Лимит 2 запроса/сек встроен в клиент. На последней странице `next_offset` приходит `0`, поэтому позиция считается самостоятельно, стоп — по `total` |
| `app/regos/catalog_sync.py` | Синхронизация каталога, цен и доступности | Ключ сопоставления — `code` REGOS с ведущими нулями (`003098`), не внутренний `id`. Витринные название, фото и привязку фасовки к карточке не трогает. Скрывает только то, чего нет в полном перечне REGOS, а не то, что выпало из фильтра |
| `app/regos/orders_push.py` | Выгрузка заказов в REGOS | Идемпотентность по `external_code` = номер заказа. Требует источника в справочнике `DeliveryFrom` |
| `scripts/sync_regos.py` | Запуск синхронизации | `--check` проверяет связь и тариф, `--dry-run` показывает изменения без записи |
| `app/migrate.py` | Досоздание недостающих колонок | `create_all()` создаёт таблицы, но не добавляет колонки в существующие. На сервере база с заказами, пересоздать её нельзя. Когда изменений станет больше десятка — заменить на Alembic, а не растить дальше |
| `app/admin_auth.py` | Вход по логину и паролю | PBKDF2 со случайной солью, `compare_digest` вместо `==`, сессии в базе (отзываются при смене пароля), защита от перебора. Для несуществующего логина хеш всё равно считается — иначе по времени ответа видно, какие логины есть |
| `app/admin.py` | Панель: товары (SA-01) и заказы (SA-04) | Вход по Telegram-id из `ADMIN_TELEGRAM_IDS`. Постороннему отвечает 404, а не 403 — чтобы по ответу нельзя было понять, что панель есть. Публикация запрещена, если ни у одной фасовки нет цены (BR-34, BR-37). Переходы состояний заказа ограничены таблицей: выполненный заказ нельзя вернуть в сборку |
| `static/admin.js` | Интерфейс панели | Вход только из витрины: Mini App открывается по корневому адресу, адресной строки в Telegram нет, а в браузере подпись не придёт. Кнопка «Панель» в витрине появляется, только если сервер признал вас администратором |
| `scripts/import_photos.py` | Раскладывает фото по кодам REGOS | Файлы прототипа названы `p-003098.jpg` — это код номенклатуры. Сохраняются как `{product_id}.jpg`, чтобы код REGOS не утёк в публичный адрес (BR-36) |
| `static/app.js` | Каталог, карточка, корзина, оформление, «Мои заказы» | Навигация: три корневых раздела в нижнем меню (`ROOT_SCREENS`) плюс экраны поверх них. Отступы снизу задаются классами `tabs-on` / `action-on` на `body` — иначе содержимое уезжает под меню и кнопку. Корзина и ключ попытки лежат в `localStorage` (`rozmart.cart.v1`) и переживают перезапуск. Корзина сверяется с сервером при открытии. Максимум 99 штук одной позиции — столько же принимает сервер. Подпись Telegram уходит заголовком `X-Telegram-Init-Data`. Полный экран — только с Bot API 8.0, на клиенте постарше молча остаётся шторка |

Ещё не сделано: оплата, рабочие места оператора и курьера (`staff.html` в прототипе), а из админки — экраны SA-02, SA-03, SA-05…SA-09 (акции, параметры, роли, отчёты, отзывы, журнал действий, финансовая сверка).
Как они должны выглядеть — макеты в `design/`, там же про их актуальность.

Номера заказов выдаёт отдельный счётчик (`counters`, см. `app/orders.py`): `UPDATE … RETURNING`
берёт блокировку на строке счётчика, поэтому два одновременных заказа получают разные номера.
До этого номер выводился из `id` строки, и на PostgreSQL параллельные заказы ломались
об уникальный индекс по пустому `number`.

## Запуск

```
.venv\Scripts\activate
set TELEGRAM_AUTH_DISABLED=1
uvicorn app.main:app --reload
```

Проверка: http://127.0.0.1:8000/health

`TELEGRAM_AUTH_DISABLED=1` выключает проверку входа: на своей машине Telegram нет и подписать
данные нечем. Без этой переменной приложение откажется стартовать и скажет, чего не хватает.

## Переменные окружения

| Переменная | Зачем |
|---|---|
| `BOT_TOKEN` | Токен бота из BotFather. Им проверяется подпись Telegram. На сервере обязателен |
| `TELEGRAM_AUTH_DISABLED` | `1` — работать без проверки входа. Только для разработки |
| `DATABASE_URL` | Другая база вместо SQLite, например `postgresql+psycopg://…` |
| `REGOS_KEY` | Ключ локальной интеграции REGOS. Кабинет: Настройки → Интеграции → поле «API», последний сегмент URL. Равносилен паролю к учётной системе |
| `REGOS_STOCK_ID` | Склад магазина. По умолчанию 5 (СКЛАД RDB) |
| `REGOS_PRICE_TYPE_ID` | Тип цены этого же магазина. По умолчанию 5 |
| `REGOS_ITEM_GROUPS` | Группы номенклатуры через запятую. Пусто — весь каталог, а это 8050 позиций |
| `REGOS_ORDER_FROM_ID` | Источник заказов из справочника `DeliveryFrom`. Не задан — выгрузка заказов выключена |
| `ADMIN_TELEGRAM_IDS` | Telegram-id администраторов через запятую. Пусто — панель закрыта для всех |
| `API_DOCS` | `1` — включить `/docs` и `/openapi.json`. На сервере выключено: схема показывает посторонним устройство сервиса |
| `NOTIFY_BOT_TOKEN` | Токен **информационного** бота — того, что пишет покупателю о заказе. Это другой бот, не `BOT_TOKEN`. Пусто — уведомления выключены |
| `NOTIFY_WEBHOOK_SECRET` | Секрет, которым Telegram подписывает обновления. Без него приложение их отвергает |
| `PUBLIC_URL` | Адрес сайта, по нему регистрируется вебхук бота |

## База данных

Разработка идёт на SQLite — файл `rozmart.db` создаётся автоматически при запуске.
Для другой базы задайте переменную окружения `DATABASE_URL`, код менять не нужно:

```
set DATABASE_URL=postgresql+psycopg://user:pass@host/rozmart
```

**Важно:** миграций пока нет. После изменения моделей в `app/models.py` удалите
`rozmart.db` и запустите сервер заново — иначе новые колонки не появятся,
а ошибка вылезет позже и в неочевидном месте.

Каталог после этого заливается заново:

```
.venv\Scripts\python.exe -m scripts.import_catalog
.venv\Scripts\python.exe -m scripts.export_catalog
```

## Интеграция с REGOS

Каталог, цены и доступность приезжают из учётной системы REGOS. Ручная заливка
из Excel больше не нужна.

```
set REGOS_KEY=<ключ из карточки интеграции>
.venv\Scripts\python.exe -m scripts.sync_regos --check      проверить связь и тариф
.venv\Scripts\python.exe -m scripts.sync_regos --dry-run    посмотреть, что изменится
.venv\Scripts\python.exe -m scripts.sync_regos              синхронизировать
```

**Цена в REGOS привязана к магазину через тип цены, а не к складу.** На каждую
точку заведён свой тип: склад 1 SAMPI → тип 1, склад 4 ASKIYA → тип 4,
склад 5 RDB → тип 5, склад 6 SAGBAN → тип 6. Пара `REGOS_STOCK_ID` /
`REGOS_PRICE_TYPE_ID` обязана быть согласованной. Если не передать тип цены,
REGOS молча возьмёт первый по id — то есть цены SAMPI для любой точки.

**В REGOS нет витринного товара с фасовками.** «Экстра варёная» на витрине —
это четыре отдельные позиции REGOS (400, 455, 700 и 855 г). Группировку задаёт
человек, и синхронизация её не переписывает: новая позиция падает скрытой
карточкой в категорию «Новые из REGOS», а контент-менеджер переносит фасовку
в нужную карточку, задаёт название и фото и публикует (BR-34).

**Что синхронизация не делает.** Не удаляет товары — только снимает с публикации:
на фасовку ссылаются оформленные заказы (BR-09). Не трогает витринные название,
описание, состав и фото: это ручная работа, и затирать её выгрузкой нельзя.

### Выгрузка заказов

Оформленные заказы уходят в REGOS документом `DocOrderDelivery`. Отправляет либо
оператор кнопкой в карточке заказа, либо витрина сама сразу после оформления —
переключатель в панели, «Состав каталога» → «Отправка заказов в REGOS».

**Интеграция доводит документ только до статуса «Утверждён» и останавливается.**
После этого заказ виден кассиру в списке на приём. Кассу и статус «В обработке»
проставляет сама касса, когда кассир нажимает «Принять».

Чего делать нельзя, проверено на живых заказах:

| Действие | Что происходит |
|---|---|
| `SetOperatingCash` — привязать кассу заранее | заказ уходит из общего списка, кассир его не видит |
| `SetStatus Paying` — перевести в «Оплата (продажа)» | состояние означает «уже взят в оплату на конкретной кассе», в очереди на приём его нет |

Оба шага были в первой версии, и заказы неделю не доходили до кассира, хотя
в REGOS выглядели проведёнными. Ориентир — заказы от Uzum: они приходят
без кассы и ждут приёма.

Повторная отправка дубля не создаёт: перед созданием проверяется `external_code`,
куда кладётся номер заказа витрины (`RB-8009`).

Отправка идёт после ответа покупателю и в отдельной сессии базы: недоступная
учётная система не должна мешать оформлению. Не получилось — заказ остаётся
в панели с текстом ошибки и кнопкой ручной отправки.

### Статус из REGOS возвращается в витрину

Выгрузка доводит заказ до «Утверждён» и останавливается, но дальше он живёт
в REGOS своей жизнью: кассир принимает его, пробивает оплату, закрывает или
отменяет. Раз в минуту `app/regos/orders_sync.py` забирает статусы выгруженных
незакрытых заказов одним запросом и переносит их на витрину, а покупателю
уходит сообщение — тем же путём, что и при смене состояния оператором.

| REGOS | Витрина |
|---|---|
| 23 Утвержден | Принят |
| 24 В обработке | Собирается |
| 25 Оплата (продажа) | В доставке |
| 26 Завершен | Выполнен |
| 27 Отменен | Отменён |

Статус 22 «Новый» не переносится: это состояние до подтверждения.

**Только вперёд.** Документ в REGOS может вернуться в «Новый» — так уже было
с половиной выгруженных заказов. Повторять это движение нельзя: покупатель,
которому сказали «собираем», увидел бы «ждёт оплаты» и получил бы об этом
сообщение. Поэтому состояние меняется, только если новое дальше нынешнего;
отмена — исключение, она приходит из любого места. Ручной перевод оператором
синхронизация тоже не откатывает.

Запрос один на все заказы: фильтр `id In` принимает список **строкой** через
запятую — массив тот же метод отклоняет ошибкой 1008, а операторы кроме
`Equal` и `In` для поля `id` не поддерживаются.

```
python -m scripts.sync_orders --list    показать расхождение
python -m scripts.sync_orders --quiet   выровнять без сообщений покупателям
```

`--quiet` нужен после простоя: если расхождение копилось днями, рассылать
по нему сообщения задним числом незачем.

### Отмена и удаление заказа

Отмена заказа в панели снимает его и в REGOS: уходит
`DocOrderDelivery/SetStatus` со статусом `Canceled`. Без этого отменённый заказ
остался бы в очереди на кассе, и его собрали бы и отдали курьеру.

Кнопка «Удалить» в карточке заказа убирает его из витрины совсем — вместе
с составом, суммой и неотправленными сообщениями покупателю. Документ в REGOS
при этом **отменяется, а не удаляется**: метод `DocOrderDelivery/Delete`
существует, но на любом документе — «Новый», «Утвержден», «Отменен» — отвечает
ошибкой 1009 «records to update or delete were not found». Проверено на трёх
документах и на всех вариантах параметров (`id` числом, строкой, списком,
`ids` списком). Похоже, ключу локальной интеграции удаление документов
не разрешено. Для кассира разницы нет: по отменённому заказу он ничего
не отгружает.

Если отменить в REGOS не удалось, заказ не удаляется и из витрины: иначе
на кассе остался бы живой документ, о котором в витрине уже нечего вспомнить.
Оператор увидит текст ошибки и решит, что делать.

Удаление необратимо и уносит заказ из истории. Это инструмент для тестовых
и ошибочных заказов, а не способ убрать неудобную выручку из отчётов.

### Что приезжает в карточку заказа на кассе

Покупатель, телефон, адрес, дата и способ доставки, примечание с номером заказа
и комментарием. Курьер не заполняется — его назначает кассир кнопкой
«Назначить курьера».

Имя покупателя в карточке REGOS пишется латиницей: API не принимает кириллицу
в именах и отвечает ошибкой 9999 (см. `app/regos/translit.py`). Исходное имя
целиком остаётся в примечании документа.

### Фотографии из REGOS

У номенклатуры REGOS бывает картинка — `ItemImage/Get` отдаёт ссылку на неё
в их CDN. Из 8050 позиций такие нашлись у 167, и это почти весь наш
ассортимент: из опубликованных фасовок картинка есть у 43 из 49.

Загружает их кнопка в панели: «Состав каталога» → «Фотографии из REGOS».
Рядом кнопка «Посмотреть, сколько найдётся» — она ничего не скачивает,
только считает.

Кнопкой, а не при синхронизации каталога, и это осознанно: это десятки
скачиваний по несколько сотен килобайт, а картинки в учётной системе меняются
раз в год — гонять их каждые полчаса незачем.

Уже загруженные вручную фотографии не трогаются никогда: свои сняты и обрезаны
под витрину, а в REGOS лежит то, что удобно кассиру. То же правило, что
у названий и описаний — выгрузка не затирает ручную работу.

Файл по-прежнему называется по id карточки (BR-36), картинки крупнее 4 МБ
и неизвестных типов пропускаются, код REGOS в публичный адрес не попадает.

### Инкрементальной выгрузки нет

Фильтр по `last_update` на текущем тарифе отклоняется с ошибкой 7501
(«работа с дополнительными полями»). Поэтому синхронизация каждый раз проходит
каталог целиком: 8050 позиций — это 17 страниц по 500, около полутора минут.
Когда понадобится реальное время, подключать вебхуки `ItemAdded` / `ItemEdited`
и догрузку пропусков через `Event/Get` — тарифная опция `webhook_able` включена.

## Обновление свайпом

Браузерного «потянуть, чтобы обновить» в Telegram нет и не будет: вертикальный
свайп там принадлежит самому Telegram — им приложение сворачивают. Мы этот
жест отключаем (`disableVerticalSwipes`), иначе приложение закрывалось бы
при каждом промахе мимо списка, — и используем освободившийся жест сами.

Тянут сверху вниз от начала списка — перечитывается то, что на экране: каталог
со стоимостью доставки, корзина, заказы или профиль. Жест срабатывает только
от самого верха (иначе он спорил бы с прокруткой) и только если оттянули
больше 70 пикселей; палец при этом проходит вдвое больше, чем едет значок, —
так жесту труднее сработать от случайного касания.

## Точка на карте

Покупатель может показать дом на карте — кнопка «Указать на карте» под полем
адреса, в оформлении заказа и в профиле. Адрес строкой это не заменяет: по нему
подъезд, этаж и квартира, а карта нужна, чтобы курьер нашёл дом.

Карта — Leaflet, библиотека лежит в `static/vendor/` и подгружается только при
открытии карты: тянуть её ради каталога незачем, а сторонний CDN — лишняя точка
отказа там, где связь и так небыстрая.

Видов два, переключатель слева сверху, выбор запоминается в браузере:

| Вид | Тайлы | Зачем |
|---|---|---|
| Спутник (по умолчанию) | Esri World Imagery | свой дом узнают по крыше и двору, в махаллях названий улиц часто нет |
| Схема | OpenStreetMap | когда нужен общий план и названия |

Ключей ни один слой не требует, но указание источника обязательно для обоих —
оно в углу карты.

**Почему не CARTO.** Сначала схемой был CARTO Voyager, а поверх спутника шли
их же светлые подписи — выглядело заметно лучше. В сентябре 2026 CARTO закрыли
бесплатную отдачу: тайлы стали приходить с водяным знаком «API KEY REQUIRED»
через всю карту. Вернуться к ним можно только с ключом от их тарифа.

Из бесплатных схем по Ташкенту годится только OpenStreetMap: у Esri World
Street Map здесь пусто — на месте кварталов один-два названия улицы. Подписей
поверх спутника поэтому сейчас нет; вместо них под картой словами показывается
адрес найденной точки.

Если понадобится настоящий гибрид со знакомыми названиями — это Яндекс.Карты
или 2ГИС, оба по ключу, оформленному на владельца магазина.

### Адрес по точке

Когда карта останавливается, адрес под булавкой определяется сам и показывается
внизу экрана; по кнопке «Готово» он попадает в поле адреса. Геокодер —
Nominatim (OpenStreetMap), см. `app/geocode.py`. Ключа не требует, но просит
не чаще запроса в секунду и просит представляться, поэтому:

* запрос идёт через наш сервер, а не из браузера: ограничитель один на всех,
  кэш общий, и в Nominatim видно одно приложение, а не сотню телефонов;
* адрес спрашивается не на каждый сдвиг, а через секунду после остановки;
* ответы кэшируются по точке с округлением до метра;
* на отказ (429/403) геокодер не трогаем десять минут.

Найденное подставляется сразу, без вопросов: точка на карте и есть ответ
на «куда везти», и человек, который её поставил, ждёт адрес в поле, а не ещё
одну кнопку. Прежний текст в поле при этом заменяется.

Не нашлось или геокодер молчит — поле остаётся за покупателем, как было
раньше. Заказ от этого не страдает.

### Дом, подъезд, квартира

Отдельные поля рядом с адресом — раньше всё это писали одной строкой,
и квартиру в ней просто забывали. Номер дома приходит с карты в своё поле
(геокодер отдаёт его отдельно от улицы), подъезд и квартиру знает только сам
покупатель.

В базе покупателя части лежат отдельно (`customers.house/entrance/flat`)
и подставляются в следующий заказ. В заказе адрес хранится одной строкой —
её собирает сервер (`ContactIn.full_address`), потому что читают её курьер,
касса и REGOS, и выглядеть везде она должна одинаково:

    Шарк Тонги улица, Чиланзар-16, дом 39, подъезд 3, кв. 42

Точку ставят не перетаскиванием маркера, а движением карты под неподвижной
булавкой: на телефоне так попадают точнее.

### Кнопка «где я»

Самое хрупкое место карты, поэтому подробно.

**Разрешение не спрашиваем сами.** Автоматически координаты берутся, только
если доступ уже выдан: `LocationManager.isAccessGranted === true` в Telegram,
`permissions.query` со состоянием `granted` вне его. Иначе ждём нажатия кнопки.
Раньше карта запрашивала местоположение при каждом открытии — и покупатель
видел вопрос о доступе на каждый заказ.

**Ответ показываем.** Появляется синяя точка и круг точности. Без них, если
человек и так стоял рядом, карта почти не двигалась, и казалось, что кнопка
не работает. При точности хуже 120 м не приближаем вплотную — иначе булавка
уверенно встанет не на тот дом.

**Отклик сразу.** Значок начинает крутиться по нажатию, до первого запроса:
Telegram отвечает не мгновенно, и секунды молчания выглядят как поломка.
Если `LocationManager` не отзывается за 2,5 секунды, уходим на браузерный
запрос; если доступ закрыт — предлагаем открыть настройки Telegram.

Ответ приходит с задержкой в пару секунд, поэтому если карту уже подвинули
руками, автоматический ответ игнорируется: иначе карта уезжает из-под уже
выбранной точки.

Координаты хранятся у заказа (`orders.lat/lon`) и в профиле покупателя,
округлённые до шести знаков — это около 10 см, дальше идёт дрожание пальца.
Из профиля они подставляются в следующий заказ.

Точка уходит:

* **в REGOS** — поле `location` документа, объектом `{latitude, longitude}`.
  Строкой «широта,долгота» тот же метод не принимает (ошибка 1008), а объект
  сохраняется и читается обратно — проверено на живом документе;
* **в сообщение сотрудникам** — ссылкой рядом с адресом, открывается
  и Google, и Яндекс.Картами;
* **в карточку заказа в панели** — там же, ссылкой.

## Служебный бот

Второй бот, `@rozmartinfobot`. **Покупателям он не пишет ничего** — это бот
для магазина: сюда приходит каждый новый заказ с составом, контактами
и адресом и сообщение об отмене. Код: `app/notify.py` (отправка) и `app/bot.py`
(приём «Старта» и список чатов).

Покупатель следит за своим заказом в самом приложении: в «Моих заказах»
над каждым заказом нарисован его путь — принят, собирается, в доставке,
выполнен, — пройденные шаги отмечены. Отменённый заказ показывается
отдельной строкой, в цепочку он не встраивается.

Нажатие на заказ открывает его карточку целиком: путь крупными значками,
состав с фотографиями, суммы, адрес, телефон, время, способ оплаты
и комментарий. Раньше состав раскрывался прямо в списке, и на телефоне
это складывалось в простыню, из которой ничего не выудить.

Почему отдельный бот, а не тот, через который открывается магазин: у них разные
задачи и разное время жизни. Магазинным токеном проверяется подпись входа
в приложение — смена его ради уведомлений разлогинила бы всех покупателей.

### Бот не может написать первым

Это ограничение Telegram, а не нашего кода: пока чат не написал боту,
`sendMessage` отвечает `403 bot can't initiate conversation with a user`.
Поэтому порядок такой:

1. сотрудник пишет боту «Старт» — или бота добавляют в рабочую группу;
2. чат появляется в списке в панели (имя, `@имя`, личный он или группа);
3. администратор нажимает «Дать доступ».

Сообщения, накопившиеся до выдачи доступа, досылаются, но не старше суток:
ворох вчерашних заказов в свежеподключённом чате только запутает.

### Кому приходят заказы

В рассылку попадает только чат, которому доступ выдали в админ-панели:
«Состав каталога» → «Кому приходят заказы». Сам себе его выдать нельзя,
и кода, который можно переслать, тоже нет — в карточке заказа телефон
и адрес покупателя, и подписаться на такое по своему желанию не должен никто.

Человеку, написавшему боту просто так, бот отвечает, что чат служебный,
и подсказывает покупателю смотреть заказ в приложении.

Порядок такой: сотрудник пишет боту (или бота добавляют в рабочую группу) —
чат появляется в списке панели — администратор нажимает «Дать доступ».
Работает и личный чат, и группа: в группе заказы видит вся смена сразу.

Отзыв доступа действует немедленно, в том числе на сообщения, которые уже
стоят в очереди: право проверяется в момент отправки, а не когда сообщение
поставили в очередь.

Таблица `notify_subscribers` осталась от прежней, покупательской версии бота
и больше не используется — её можно удалить руками.

### Что в сообщении

Состав, сумма, получатель, телефон, `@имя` в Telegram, адрес со ссылкой
на точку карты, время доставки, способ оплаты и комментарий — всё, по чему
заказ собирают и везут.

`@имя` сохраняется вместе с заказом (`orders.telegram_username`) — его берут
из подписи Telegram при оформлении. Именно сохраняется, а не подтягивается
заново: человек меняет его когда угодно, а в заказе должно остаться то,
по которому с ним связывались. В карточке заказа в панели оно показано
ссылкой: оператору по нему писать, когда покупатель не берёт трубку.
У заказов, оформленных до появления поля, имя берётся из подписки на бота.
Аккаунт без `@имени` — обычное дело, тогда строки просто нет.

### Очередь, а не прямая отправка

Сообщение кладётся в таблицу `notifications` и уходит фоном. Прямая отправка
из обработчика запроса означала бы, что недоступный Telegram задерживает ответ
покупателю, а перезапуск службы посреди отправки теряет сообщение молча.
Поток разбирает очередь раз в 30 секунд; свежее сообщение уходит сразу,
не дожидаясь прохода.

Постоянные отказы (бот заблокирован, чат удалён) не тратят попытки: подписка
помечается неактивной, и человек вернётся в неё сам, нажав «Старт» заново.

### Настройка

```
python -m scripts.setup_bot          зарегистрировать вебхук и описание бота
python -m scripts.setup_bot --show   что сейчас зарегистрировано
python -m scripts.setup_bot --remove отключить
```

Вебхук идёт на `PUBLIC_URL + /tg/hook` и принимается только с заголовком
`X-Telegram-Bot-Api-Secret-Token`, равным `NOTIFY_WEBHOOK_SECRET`. Без проверки
секрета любой желающий слал бы через нашего бота сообщения незнакомым людям.

## Административная панель

Адрес: `/admin`, форма входа — `/admin/login`.

Войти можно двумя способами, они работают одновременно:

**Логин и пароль** — из обычного браузера, с компьютера. Пароль хранится
хешем PBKDF2-HMAC-SHA256 со случайной солью; сессия живёт 12 часов в куке
`HttpOnly; Secure; SameSite=Lax`. Сессии лежат в базе, а не в подписанной куке,
чтобы их можно было отозвать: смена пароля закрывает все открытые.
После семи неудачных попыток логин блокируется на пятнадцать минут.

```
cd /opt/rozmart
sudo -u rozmart .venv/bin/python -m scripts.admin_user add ivan --name "Иван"
sudo -u rozmart .venv/bin/python -m scripts.admin_user passwd ivan
sudo -u rozmart .venv/bin/python -m scripts.admin_user list
sudo -u rozmart .venv/bin/python -m scripts.admin_user disable ivan
```

Пароль вводится в терминале и не принимается аргументом командной строки
намеренно: аргументы видны в списке процессов любому пользователю сервера
и оседают в истории оболочки.

**Telegram** — с телефона, без ввода пароля: подпись там уже есть. Добавьте свой
Telegram-id в `ADMIN_TELEGRAM_IDS`, и в витрине появится кнопка «Панель».
Узнать id: `/api/admin/whoami` — метод сообщает только ваш собственный.

```
ADMIN_TELEGRAM_IDS=123456789,987654321
systemctl restart rozmart
```

**SA-01 «Категории и товары».** Вкладки: не разобранные, готовые к публикации
(есть цена), на витрине, все. Поиск идёт и по витринному названию, и по коду
REGOS — администратор чаще приходит из учётной системы с кодом на руках.
В карточке правятся название, категория, описание, состав, срок годности, фото;
там же видны фасовки с их кодами и ценами. Фасовку можно перенести в другую
карточку — так из нескольких позиций REGOS собирается одна витринная.

Цены и остатки в панели не редактируются намеренно: они приезжают из REGOS,
и ручная правка будет затёрта ближайшей синхронизацией.

**«Состав каталога».** Здесь администратор сам решает, что попадает в витрину:
отмечает нужные группы номенклатуры REGOS и правит категории. Настройка живёт
в базе, а не в переменной окружения — менять её должен контент-менеджер, без
доступа к серверу и перезапуска службы. Ничего не отмечено — приезжает весь
каталог сети, а это 8050 позиций.

Кнопка «Убрать лишнее» удаляет карточки вне выбранных групп. Удаляются только
никогда не публиковавшиеся: опубликованный товар снимают с витрины осознанно.
Если на фасовку ссылается заказ, внешний ключ на `RESTRICT` не даст её удалить —
история заказов защищена схемой, а не аккуратностью кода. Перед удалением
показывается, сколько именно карточек уедет.

**SA-04 «Заказы».** Список с фильтром по состоянию, поиск по номеру, имени и
телефону, состав заказа и перевод в следующее состояние. Переходы ограничены:
`NEW → CONFIRMED → ASSEMBLING → DELIVERING → DONE`, отмена доступна на любом
шаге до завершения. Без этого выполненный заказ случайным нажатием вернулся бы
в сборку и отчёты разошлись бы с фактом.

## Каталог на сервере

Сам файл базы в репозиторий **не едет** — в нём телефоны и адреса покупателей,
а из истории git их потом не вычистить. На сервере база создаётся пустой и

после каждой заливки каталога. Изменения цен при этом видны в истории.
